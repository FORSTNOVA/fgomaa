# FGO-MAA 的 Laplace 接入

客户端通过 `src/strategy/laplace.py` 调用随客户端发布的真实 Chaldea Laplace 引擎。日常与周常出击入口强制执行战斗计算；前端 `/api/auto_team` 返回相同的校验结果。计算失败、数据不完整、运行时缺失、超时或取消都不会放行出击。

计算器先在最低伤害浮动 0.9 下执行当前推荐及动态充能顺序，将实际使用的技能整理成固定方案，再关闭动态补救并严格重放。重放通过后，将技能顺序用于正式战斗；已冷却的技能不会留在执行方案中。实际技能执行失败、主核 NP 未识别或不足 100%、本面未按计划清场时停止自动操作。

选定关卡后，按准确敌人职阶与Laplace共用的职阶关系常量排序，优先完全克制、再泛用克制与等倍；同档才比较练度和综合分。最多选6名连发打手，并为完全克制和后续候选保留试算名额。每名打手除原推荐外，还会选择不同用途的已持有礼装代表：初始NP、初始NP＋对应色卡（包括A'）、NP获得量、每回合NP、宝具威力、零初始NP高宝威与纯色卡。每类保留代表，不穷举背包所有礼装。万华镜按实际80%/100%初始NP计算，A'按实际50%/60%与等级、满破状态计算；仓库与未持有礼装不参与。

同一打手的礼装变体分别经真实引擎重放。找到可行方案后，额外校验尚未尝试的零初始NP高宝威方案；只有三波NP、伤害均通过且最低伤害裕量更高，才采用黑之圣杯这类礼装。失败保留已通过方案，不自动降成普攻补刀。返回的 `laplace.attempts` 记录打手、礼装、克制关系及每次通过/失败原因。

## 低血量周回

1–3 波、各敌人 HP 不超过 60000 的目标会额外尝试最多三个三打手候选：两名自有打手加一名指定助战，按各波职阶安排不同从者开宝具。自充、附加充能、已持有初始 NP 礼装只用于候选排序，能否开宝具和清场仍由真实引擎判定。同一礼装没有确认多份持有时不会重复分配；退场换人型打手，以及充能依赖尚未导入的灵基切换状态的妖兰，暂不参与此候选。

各敌人 HP 不超过 5000 时还会尝试一个无需初始 NP 的普攻候选。普攻校验在最低伤害浮动、无暴击下枚举前排十五张卡的全部 2730 个有序三卡组合，任一组合不能清场、遇到超出保守范围的机制或校验超时，就尝试宝具方案。每个组合从独立战斗快照开始；进入后续波次时采用保证获得的最低 NP、不计星星，并保守处理次数增益，防止代表性选卡带来虚假的后续收益。普攻方案也必须固定重放通过。

通过后，每回合行动会明确显示为指定位置宝具或普通攻击。普通攻击只点击三张普通卡；轮换宝具只点指定位置的一张宝具及两张垫卡。不会自动追加其他助战宝具。低血量与连发候选一起按各波打手克制关系安排试算；全部未通过则停止出击。并非血量低就强行普攻，多敌人或依赖特定发牌的波次通常会采用宝具。

该组件保留 Flutter 引擎以运行 Laplace 所依赖的 `dart:ui`，客户端运行不调用 Flutter/Dart SDK、上游测试脚本或试验目录。`runtime/laplace/` 包含运行文件、版本清单、许可证、依赖通知与对应源码。计算任务的必要账号字段仅存于本地 `.app_profile/laplace/jobs/`，不打包到公开资源，不发送给第三方。公开游戏数据的获取仅请求关卡、从者、礼装与技能 ID。

## 构建

```powershell
python scripts/build_laplace.py --source <已完成 flutter pub get 的 Chaldea 源码目录> --publish
```

本机已准备好的源码默认位于 `scratch/laplace_trial/chaldea`，构建器读取本机 Flutter SDK。正式客户端无需该构建环境。

上游提交为 `9970a57a7d150d5d551f583f6b2c4862a9f7e798`。本地源码副本仅放宽 Flutter 补丁版本要求到 `>=3.47.4 <3.48.0`，并加入 `lib/fgomaa/` 适配入口。

## 数据范围与边界

- `data/laplace/quests.json` 保留27个内置关卡别名；全量关卡绑定由 `src/strategy/quest_catalog.py` 从Atlas国服导出自动刷新至 `.app_profile/quest_catalog/`。新增键为 `atlas_cn_<游戏ID>`，目录存在不代表导航已适配或模拟能通过。详情见主README的“全量目录同步与刷新”。
- 使用账号内实际等级、宝具、技能及分配礼装等级/满破情况；助战按宝具一、满主动技能、无礼装和附加技能假设。
- 国服接口没有敌人数据时，显式标注使用同 ID 的日服公开战斗样本。随机敌人和样本差异不等同于穷举全部关卡分支。
- 换人服目前明确使用迦勒底战斗服 Lv10；没有指定礼装但包含御主技能的方案会拒绝计算。不能将其他魔术礼装默认为等价。
- 模拟按推荐装备计算，客户端显示所需礼装与魔术礼装；本次没有新增礼装自动更换及满破状态的实机识别。游戏实际装备需要保持一致。
- 未绑定 ID、没有完整敌人数据、依赖的礼装缺少持有数据或包含尚不支持的机制时会停止。不会以空敌人列表、近似关卡或旧结果判定通关。
- 不模拟 OCR/触控失误，也不依赖敌方行动或未校验的补刀；实际失败仍由原状态机和执行检查停止。普攻的保守校验并非任意高难本机制的完整证明。
- 前置即死宝具重复使用暂不放行：固定概率门槛不能证明即死成功时的零 NP 回收分支。单次收尾宝具及伤害后的即死不受该限制；这项限制尚不是完整的概率分支模拟。

## 验证

`tests/test_laplace_integration.py` 包含真实引擎、实际 HTTP 接口、NP 与冷却方案修正、伤害不足、缺失数据补齐、旧结果、账号变化、取消与超时等检查。真实组件验证会从 PATH 中移除 Flutter SDK，证明运行阶段不依赖开发工具。

`tests/test_low_hp_planner.py` 另外验证轮换名单、礼装数量限制、指定宝具 NP 检查、普通攻击点击、全部三卡组合的真实引擎重放，以及弱队友发牌无法清场时拒绝普通攻击的反例。合成 HP 仅用于测试，不代表实机关卡验收。
